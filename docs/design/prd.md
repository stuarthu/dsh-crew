## 问题,以及谁有这个问题

`principles.md` 原则 6 是「测试先于代码，报告必须证明它」。它有一个洞：**test first 确实产出一份
测试，但那份测试是写代码的同一个人写的**，所以测试会被写成迎合他本来就打算写的代码。一个只修了
表面症状的改动照样能全绿。

这个仓库已经承认过这个洞的一半——bug 的 DoD 一节由 PM 在修之前写，engineer 不许自己写。但那只
盖住了 bug，没盖住普通任务。

**谁有这个问题**：用 dsh-crew 跑真实作业的人。他们拿到的「全绿」比它看起来的弱。

## 用户

1. **用 dsh-crew 的开发者**——他们要能选择「这一行任务值得两个人做」，并且要看得懂成本。
2. **这个仓库的贡献者**——他们要能读懂新规则从哪来、为什么，以及它不保证什么。

## 它必须做到什么

1. 每个任务可以由**两个 engineer** 做：A 只写**单元测试**，B 只写产品代码，**两人在各自的 git 工作树里同时
   开工**；A 在自己的树里拿红灯，B 闭眼写；**首次会合那一次运行在合并之后由 PM 跑**。
2. 两个 engineer **之间没有任何通道**。分歧只能经过 PM。写代码阶段 B **读不到**测试文件——
   靠两棵工作树，不靠自觉。
3. **今天的单人 test first 一个字不改**，继续可用。
4. **双人形状只存在于有 architect 的作业里**；小作业那条路没有它。哪些任务走双人由 **architect 提**，
   用户在第 5 步连同整份任务表一起盖章；PM 给默认值加例外清单，不是一行一问。
5. 每个双人任务的**接口由 architect 钉在一份 ADR 里**（import 路径、导出名、签名、返回形状、
   出错行为），A 和 B 各读自己那一半，**都不许自己改它**。
6. 新规则和它的**理由与外部证据**写进 `principles.md`，包括**它不证明什么**。
7. 用户看得见的行为变化写进两份 README 和 `CHANGELOG.md`。
8. `CLAUDE.md` 补上 flat 规则的**第四道守卫**——`send_message` 的血缘检查
   （`dsh-subagent/lib/index.js:1337-1338` 抛 `UNAUTHORIZED`），今天那里只写了三道。

## 三种写测试的角色必须分清（v2 加入）

用户点出的风险：`crew_test_engineer` 这个名字容易被读成「测试员」，也就是 QA。**它不是。写测试的
engineer 是程序员，写的是单元测试；QA 是另一个角色，写的是 QA 用例。** 这个区分在仓库里结构上已经
存在（`roles/qa.md:24`：「你的用例只住在 `docs/qa/` 下面，别的地方都不行」），但**没有一处把三者
并排写清楚**，而现在多了一个角色，不写清楚就会混。

| | `crew_test_engineer` | `crew_code_engineer` | `crew_qa` |
| --- | --- | --- | --- |
| 是什么人 | **程序员** | 程序员 | **QA** |
| 写什么 | **单元测试** | 产品代码 | **QA 用例**（验收/黑盒） |
| 住在哪 | **项目自己的测试套件**，是这个任务拥有的文件，跟代码一起提交 | 产品代码文件 | **`docs/qa/<task-id>/`，别处都不行** |
| 什么时候 | 代码存在**之前** | —— | 代码完成**之后** |
| 看得见代码吗 | 看不见（它在自己的工作树里，代码还不存在） | —— | 先写计划再读代码 |
| 管多大范围 | **只管这一个任务** | 只管这一个任务 | 这个任务，**外加把过去每个任务的用例全跑一遍**（回归） |

**四条区别，缺一不可**：粒度（单元 vs 验收）、时机（之前 vs 之后）、家（项目套件 vs `docs/qa/`）、
范围（本任务 vs 全部回归）。

**因此本作业必须做到：**

1. 两个新角色的 `summary`（`host/roles.js` 里 PM 看到的那一行）**必须自己就能区分**。
   `crew_test_engineer` 的 summary 要点明「单元测试」和「在代码之前」。
2. `crew_qa` 现有的 summary 是 `"Test the result against the document"`——它没提 `docs/qa/`，
   在三个角色并存之后不够分。**这一行也要改**，虽然 QA 的行为一个字不改。
3. `roles/test-engineer.md` 开头就要写明：你是程序员，不是 QA；QA 是另一个角色，在你之后跑，
   用例写在 `docs/qa/` 下面。
4. 上面那张表要进 `principles.md` 原则 21，以及两份 README。

## 用词表，和一次有边界的用词清理（v3 加入）

用户要求：文档里的用词必须精确，把单元测试和 QA 那一类分开。

**先更正一个说法。** 用户说的是「unit tests 和 qa tests」。**不要用「QA test」这个词**——它把
「test」这个字又放回来了，等于把刚分开的两样东西重新粘在一起。这个仓库**已经**用了两个不同的名词，
而且很干净：

- `roles/qa.md` 里 **case / 用例** 出现 51 次，**「QA test」出现 0 次**。
- **「unit test」今天已经在用**，四个文件里都有：`README.md`、`roles/pm.md`、
  `principles.md`（原则 13「Every test lands on disk and runs again」）、`roles/engineer.md`。
  （**这里原来写的是四个行号**——`README.md:203`、`roles/pm.md:357`、`principles.md:322`、
  `roles/engineer.md:63`。四个全都会在这次作业里失效：那三个文件分别归 T-59、T-62、T-55，
  而 `principles.md` 的原则 6 在 T-52 里长了 34 行，`:322` 已经变成 356。按小节和原文引用，
  不按行号——规则见 `principles.md` 原则 20。）

所以正确的一对是 **unit test（单元测试）** 对 **case（QA 用例）**——两个不同的名词，混不起来。
本作业沿用它，不发明新词。

**真正缺的东西：仓库里没有任何一处用词表。** 我搜过，没有 glossary、没有「术语」小节。三个角色都写
「测试」之后，没有用词表就没有一个可以指的地方。

### 要加的用词表（四条）

| 词 | 指什么 | 谁写 | 住在哪 |
| --- | --- | --- | --- |
| **单元测试**（unit test） | 一个行为一个测试，代码存在之前写 | `crew_engineer` 或 `crew_test_engineer` | 项目自己的测试套件，是任务拥有的文件 |
| **QA 用例**（case） | 验收/黑盒，代码完成之后写 | `crew_qa` | **只在** `docs/qa/<task-id>/` |

**规则**：一句话如果可能指其中两样，就必须用精确的名词。**光写「test / 测试」只允许出现在故意指
「上面任意一种」的地方。**

### 清理的边界——这一条是硬的

**「措辞可改、规则不可改」**：这次清理只换名词，不动任何规则、门槛、流程或散文钉子的原话。

**只清理本作业本来就要动的文件**：`principles.md`（原则 6、原则 21、用词表本身）、三份 engineer
persona、`roles/pm.md` 新长出来的那个分支、`roles/code-reviewer.md`、`CLAUDE.md`、两份 README。

**明确不在范围内：把整个仓库里每一个 bare「test」都改掉。** `roles/pm.md` 一千两百多行、
`principles.md` 一千多行，全库改字是一次巨大且危险的改动，而且大部分位置今天并不含糊（只有一个
engineer 时「test first」是清楚的）。**含糊是新角色带进来的，所以清理跟着新角色走。**

**目标**：`crew_test_engineer` 和 `crew_code_engineer` 这两个名字端到端接通——角色表、每一条
deny 列表、preset、真挂载——`npm test` 全绿。persona 先写成**占位但合规**的（够长、无 `{{`、
说明只跟 PM 说话），真内容在 M3。

**为什么它是第一个**：按 `CLAUDE.md` 设计规则 3，一个 deny 或 allow 列表里的名字如果 preset
没有，dsh 会在子 agent 启动时拒绝它——那是**那个角色的全面瘫痪**，不是警告。这是整件事最便宜的
翻车点，所以先撞它。这个任务一个人做，别的任务全部等它。

**DoD**

1. `host/roles.js` 的 `ROLE_TOOL_NAMES` 有这两个名字，`ROLES` 有对应两项，每项**只有** `allow`
   或 `deny` 之一。检查：`node tools/verify-mount.mjs` 绿。
2. 两个新角色都保留 `bash`（它们要跑代码）。检查：`node tools/verify-mount.mjs` 的 bash 检查
   **点名三个** engineer 角色；把任一个的 `bash` 删掉，它必须变红。QA 用例证明这一点。
3. `preset/crew/agent.cordis.yml` 真的挂上这两个角色工具。检查：`verify-mount.mjs` 的真挂载
   那一段通过，且**不是 skip**（这台机器有软链接）。
4. 每一条 deny 列表都拒掉这两个新 `crew_*` 名字（flat 规则）。检查：`verify-mount.mjs`。
5. 两份 persona 文件存在、超过 500 字符、不含 `{{`、写明只跟 PM 说话。检查：`verify-mount.mjs`。
6. `npm test` 六条全绿。检查：把整段输出贴出来。

### M3 — 两份 persona 写实

**目标**：A 和 B 的真实行为规则。

**DoD**

1. `roles/test-engineer.md`：只写**单元测试**文件；**在自己那棵工作树里**，路径由 brief 给；不碰 git；跑一次拿红灯；**不许**为消除冲突弱化断言（只有 PM
   能批，改动要能追回 DoD 原话）；只跟 PM 说话；不许跟另一个 engineer 通气。
2. `roles/code-engineer.md`：只写产品代码；**在自己那棵工作树里干活，树里没有测试文件**；不碰 git；干活期间跑 lint、类型检查、
   **项目的测试命令**、编译，但**不跑新行为的单元测试**；**它跑不到 A 的单元测试**；
   首次会合那一次由 PM 在合并之后跑，**跑的是 A 写的那些单元测试**（项目的测试命令会一起跑它们时
   就跑项目的测试命令），**只跑这一次**；
   红了之后 B 被叫到合并后的树里修；只跟 PM 说话。
3. 独立性怎么写：写代码阶段说成**真隔离**（两棵树），合并之后说成**已结束**。不许含糊成
   「大概不会看」。
4. `roles/engineer.md` 开头加一句指路，说明它是单人形状那一条路。**规则一个字不改**——只允许改
   含糊的**措辞**（v3 的用词清理），不允许改任何规则、门槛或流程。散文钉子原话不动。
5. `roles/test-engineer.md` 开头写明**它是程序员不是 QA**，写的是**单元测试**，住在项目自己的测试
   套件里；QA 是另一个角色，在它之后跑，用例写在 `docs/qa/` 下面。
6. 两个新角色的 `summary` 自己就能和 `crew_qa` 分开；**`crew_qa` 的 summary 也改**（提到
   `docs/qa/`），但 QA 的行为一个字不改。
   **注意：这一条的活在 M1 落地（T-51 的 DoD 第 11 条），检查在 M3 收。** 原因是三行 `summary`
   和两条新 `ROLES` 项在 `host/roles.js` 同一段代码里，而两个任务绝不共有同一个文件。
7. 检查：QA 用例逐条 grep 这些必须出现的规则；`verify-mount.mjs` 的长度与 `{{` 检查绿。

### M4 — 流程接上

**目标**：architect 会规划它，PM 会跑它，code reviewer 看得懂它的证据。

**新增 `roles/architect.md`**（CRD 0014）：标哪些任务走双人；为每个双人任务写一份钉死接口的 ADR。

**DoD**

1. `roles/pm.md` 第 4 步：任务行要带「形状」；第 5 步：形状随整份文档一起给用户盖章。
2. `roles/pm.md`：PM 给**默认值加例外清单**，不是一行一问；推荐必须有依据（四类之一）；成本
   写成估计。
3. `roles/pm.md`：双人形状的执行顺序——开两棵工作树并**各自补上那条 `node_modules` 软链接** →
   A、B 同时开工 → 合并 → **PM 跑一次 A 写的那些单元测试，只跑这一次，不许改了再跑、不许反复
   跑到绿**（`CRD 0012` 第 5 条，`CRD 0013` 第 4 条把这次运行交给 PM）→ 各自查自己那一半（用 `send_message` 叫醒
   同一个 agent，上下文原样在）→ 分歧交 PM → PM 定不了交用户 → 清理两棵树和两个分支。
4. `roles/pm.md`：DoD 措辞改进后的落点与谁批（第 17 条那两档）。
5. `roles/code-reviewer.md`：新证据 = A 的红灯 + B 的一次性结果 + 分歧记录；并**明写反转**——
   首次会合全绿是最好的结果，不是可疑，但它**只**证明两份理解对上了。
6. `roles/architect.md`：任务表带「形状」栏；双人任务的文件分成 A 的和 B 的两栏且不许重叠；
   每个双人任务一份接口 ADR，钉死那五件事；**只有 architect 能改它**。
7. `roles/pm.md`：小作业那条路**明写没有双人形状**。
8. 检查：QA 用例 grep 这些段落；`verify-mount.mjs` 绿。
