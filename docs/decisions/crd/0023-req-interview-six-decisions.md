# CRD 0023：`~/req` 开工访谈里用户定的六件事

## 谁提的

用户，2026-08-21，在 `apply-req` 作业开工前的访谈里。起点是一句话：

> `read ~/req, use the settings suggested in it to implement it`

`/home/stuart/req` 有两半：Part A 是用户自己写的七项要求，Part B 是把 v0.7.0 移植到
`claude-crew` 时找到的十二条发现。本作业要把两半都落进产品文件。

这份 CRD 只记**访谈里新拍下来的六件事**。`~/req` 本身要什么，写在
`docs/design/prd-2026-08-21-apply-req.md`（第 2 版，用户已确认）。

**它和另外两份 CRD 的关系**：`CRD 0019` 把苏格拉底式访谈推迟到本作业，并且把它需要的全部
内容（六种问题类型、漏斗、两种失败模式、停止规则、十条外部链接）搬进了仓库；`CRD 0020` 把
`~/req` 第 1a、1b、1c 项用在了上一件作业的**运行方式**上，但**一个字都没进 `roles/pm.md`**，
并且明确把其余几项留给本作业。两份都是本作业的输入，都不删。

## 访谈本身，写下来当证据

本作业**用了它自己要落地的那套方法**——用户在 `~/req` 第 4 项末尾写着「when you are doing
this crd, try use the above principles」。五个问题，一轮一个，各带 PM 自己的推荐答案。
中途用户问了一句「are you using socratic tech in this interview?」，PM 照实答了三处没做到的：
**漏斗反了**（第一问就很窄，从没问过开放问题）、**第 1 类「澄清」一次都没用**、
**第 3 类「理由与证据」和第 4 类「别的视角」一次都没用**。

这条自查本身就是证据，说明「六种问题类型」不是装饰：不逐类对一遍，就会漏掉整整三类。
PM 随后补的那个第 1 类问题（「你说 the prd is not correct，你看到的是什么？」）**是唯一一个
在仓库里查不到答案的问题**，而它换回来了本作业最实的两条要求——PRD 太长、版本历史不该在
PRD 里。**开放的澄清问题产出最多，而它差点被跳过。**

## 六个决定

### 一、作业中途发现一条坏掉的验收检查 —— 只追加，不覆盖

**这解决 Part B 第三条新规则（B12）和 `~/req` 第 1a 项之间的正面冲突。** 第 1a 项说 PM 定完
范围之后自己决定、不再逐事请示；B12 说「修正不是例外」，改动已确认的标准必须停下来问用户。

**定下来的**：用户确认过的原话**永不删除**。PM 写一份 CRD，把修正**标注日期后写在原话旁边**，
继续干活，并在文档里用一个**固定标题**（「修正记录」）把每一条都列出来，让用户能主动打断。
不停工，也不悄悄改。

**为什么是这一个**：另外两个选项各有一个致命处。「每次都停下来问」会让一条坏检查底下的任务
全部堵住，正是第 1a 项要消灭的东西。「按种类分开」（改措辞我自己定、改『什么算通过』就问你）
需要 PM 判断这一处属于哪一类——而**那个判断正是审计里失效的东西**：报告数出九次没有用户同意的
修改，每一次单独看都比上一次更小、都说得过去。只追加**不需要这个判断**。

**它已经用过一次了。** 本作业的 PRD 从 v1 到 v2 时，PM 发现自己把 24 项数成了 22 项——照抄了
自己上一句的数字，没有去数。这跟审计里第 14 版那一条一模一样。按新规矩改了，并且记进了
PRD 的「修正记录」表。

### 二、PRD 一件作业一份：`prd-<日期>-<作业 slug>.md`

**为什么要改**：`docs/design/prd.md` 今天是**上一件作业自己的** PRD（`paired-engineers`，
第 10 版，370 行）。下一件作业写 PRD 就会把它覆盖掉。用户第 7 项就是在说这件事。

**用户原本建议 `prd-<date>.md`，PM 指出它第一天就撞名**：上一件作业的 PRD 日期是 2026-08-21，
本作业也是 2026-08-21。

**定下来的**：`docs/design/prd-<日期>-<作业 slug>.md`。`hld` 同形。
`docs/design/tasks.md` **不动**——它本来就是全仓库一张表（T-01 到 T-62 跨四件作业），
`tools/verify-tasks.mjs` 读的就是它，而且任务号跨作业不重复，所以它一份就够。

**为什么带 slug 而不是只带日期**：日期能按时间排序，slug 保证唯一而且文件名本身就说清是哪件活。
只带日期的话，同一天两件活只能靠 `-2` 区分，一个月后没人认得出哪个是哪个。

**代价**：`prd.md` 在 **29 个文件里出现 85 次**，其中包括 `tools/verify-mount.mjs:886` 那道
**硬要求 `roles/pm.md` 里有字面量 `docs/design/prd.md`** 的检查，和 `docs/qa/T-60/case-09`
里断言这个文件存在的用例。改名会让这两处立刻变红，所以它们必须在同一个提交里改。

### 三、文件权限清单：只钉写，读不限

**用户第 3 项要的是「a list of files that each role can read/write」。** PM 拿「读要不要钉」
本身来问（第 6 类问题：质疑这个问题本身），因为 Part B 第二条新规则说的是反过来的话——
「一个角色读得宽、写得窄。读从来不是问题所在。」

**定下来的**：

1. 每份角色提示词写一段「你能写什么」，**按类写，不按具体文件名**；
2. 加一句「读不受限，而且应该多读」；
3. `roles/pm.md` 和 `principles.md` 各放一张全局表：哪类文档谁写；
4. 加上 Part B 的类规则：**判你的文档永远不在你的可写集合里**，
   **就算简报把它递过来也不写，而且要在报告里说这件事**。

**为什么必须按类、不能按文件名**：决定二让 PRD 的文件名**每件作业都变**。任何一份写死
`docs/design/prd.md` 的清单，从下一件作业起就是错的——而且它错得看不见。

**为什么不钉读**：一份读清单少写一项，角色就看不到它真正需要的上下文，**而且没有任何东西会
报错**。这个仓库最惨的几次事故都是「漏了也看不见」这一类（`docs/qa/gaps.md` 第 20 条：
QA 把测试计划写错了地方，79 条挂载检查和 92 个用例全绿，一条都没红，是 engineer 用眼睛发现的）。

### 四、取消 `quick` 通道；里程碑不等于发版

**用户第 1d 项里有一句硬要求**：「no matter how small a change is, we always need a milestone
that include a task and full qa/review cycles.」而今天 `roles/pm.md` 有三条通道，其中 `quick`
（错别字、改个名、一行修复）是 PM 自己动手、不叫 crew、不写文档。

**定下来的**：

- **`quick` 通道取消。** 只剩 `ask`（只回答，不改东西）和 `team`。
- 任何改动都得有一个里程碑，里面至少一个任务、一轮 QA、三个评审各一轮。
- **「一个里程碑」不等于发版。** 用户原本的定义是「提交 + 推送 + 打一个新版本」；
  这次改写成「**一次完整循环 + 一次提交**」，推送和打 tag 仍然各需要用户单独同意。
- 正常一件活只有**一个**里程碑。只有当组件之间的依赖逼着分几次发版时才分多个，
  那种情况下 PM **不需要**为每个里程碑单独请示提交。

**为什么代价比听起来小**：第 1b、1c 项已经把 QA 和三个评审压成各一轮、并行、只看改动的部分。
所以一个错别字的完整循环是**分钟级**，不是小时级。旧形状下它是「3 轮代码评审 + 2 轮安全评审
+ 逐任务 QA」，那才是让 `quick` 看起来必要的东西。

**为什么把发版从里程碑里摘出来**：用户原来的定义会让一个错别字的修复变成一次 npm 发布。
这个包真的会发布到 registry 上，所以这一条不是措辞问题。

### 五、那一轮 QA 的形状：先写清单，再一条一个 agent

**用户第 1c 项写的是**「pm always create 1 qa agent to write/execute/report only 1 case in
parallel」。PM 指出这里有个洞：**一个 agent 只写一条用例，那用例清单必须先存在**，而今天是
QA 自己先从 DoD 写测试计划、再把计划变成用例。

**定下来的**：

1. 先跑**一个** QA agent，它只做一件事——从 DoD 写出用例清单（测试计划），
   **不写用例、不读代码**；
2. PM 读完清单，按清单**一个 agent 一条用例**并行铺开；
3. PM 收全部报告。

**为什么不让 PM 自己按 DoD 拆清单**（那样少一轮，更快）：PM 既定标准又定怎么测，
Part B 那条「被测的一方不该出考题」的担心在那里又回来了。多花的一轮很短——写清单不读代码。

### 六、第 6 项整件交给 PM，按 websearch 写

**用户原话，两句**：

> `too long, history version should not be in the same prd. others I don't know. you websearch and tell me`

> `anyway I'm not expert on prd, you websearch and write it in principle and pm role.md`

> `so that pm knows how to right prd correctly.`

**定下来的**：第 6 项落点是**规则**——`principles.md` 加上写它的那个角色的提示词——
**不是回头修旧的 PRD**。用户明确说了自己不是 PRD 专家，把内容判断权交给 PM，依据是 websearch。

**用户自己指出的两处**（这两处不用查也成立）：PRD **太长**；**版本历史不该和 PRD 在同一份
文件里**。第二处的去处已经有了，不用新建地方：每一份 CRD 的 **Applied** 行本来就写着「改了
哪些文档、新版本号是多少」，git history 也在。所以 PRD 里那 15 行是重复的数据，
删掉不丢东西——PRD 只留一行「当前版本 + 日期」。

**websearch 回来之后加进本作业 PRD 的东西**（`docs/research/document-types.md`，717 行，
每条带出处和阅读日期）：研究指出一份 PRD 该有而本仓库的 PRD 没有的三件——
**优先级与切割顺序**（Cagan `© 2005 SVPG`：定优先级是必须的一步，因为
「schedules often slip and you may well be forced to cut some features」）、
**发布标准**（六条非功能门槛）、**时间窗口**；以及一件多的——版本历史当开头正文。
本作业的 PRD v2 三件都加上了。

**研究还带回一个冲突，本 CRD 不判它**：按 Cagan / Atlassian / Figma 的说法，带 `grep` 命令的
逐条验收检查属于**任务计划或测试计划**，不属于 PRD——这跟本仓库自己的 `CRD 0010`（DoD 是一个
章节，就长在它管的那份文档里，因为独立的 DoD 文件曾经一小时丢掉 75 条检查）直接冲突。
两边都有真实的理由。这是一个「怎么做」的决定，归 **ADR 0015**，由 architect 写。

## 它动到什么

**文档**：`docs/design/prd-2026-08-21-apply-req.md`（本 CRD 的六个决定全在里面）。

**任务**：决定二到决定五各自对应 PRD 里的 A7、A3（=B11）、A1d、A1c，
决定六对应 A6，决定一对应 B12。具体任务号由 architect 写在 `docs/design/tasks.md` 里。

## 代价

- **决定一**（只追加）会让 PRD 随作业变长，因为原话永不删除。用户判断「看得见的重复」
  比「看不见的改动」便宜。
- **决定二**（改名）要动 29 个文件 85 处，而且会让两处已有检查立刻变红。
- **决定四**（取消 `quick`）意味着一个错别字也要走完整循环。第 1b、1c 项把这个代价压到了
  分钟级，但它不是零。
- **决定五**多一轮 QA（写清单那一轮）。换到的是「出考题的人不是被考的人」。
- **决定三**只钉写不钉读，所以「评审跑到范围外去」这件事**没有**被这条规则挡住。
  它由第 1b 项的「只看改动的部分」挡，那是另一条规则，不是这一条。写下来免得以后以为它管了。
