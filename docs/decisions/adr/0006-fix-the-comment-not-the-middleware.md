# ADR 0006：把 guard 的注释改成真话，而不是把中间件扩到写文件的工具上

## 背景
安全评审指出：审批文件那条规则旁边的注释说「任何 agent 都不能写这个文件，连被信任的 PM
也不能」。这句话对**非 shell 命令**来说是假的。guard 只包 `bash` 和 `pwsh`（`SHELL_TOOLS`），
所以一个拿着 `write` 或 `edit` 的角色——工程师两个都有——可以把审批文件当成一次普通的文件
写入创建出来，这个中间件根本看不到那次调用。两份 README 抄的是同一句假话。

## 选项
- **A** 把中间件扩到写文件的工具上，让 `write` / `edit` 也过这条规则。洞真的补上了，代价是
  guard 从「一个读命令文本的安全带」变成要理解每一种能写文件的工具，而它本来就管不住
  「把推送藏在脚本里」这类做法——补一个洞，别的洞还在。
- **B** 不动中间件，把注释和两份 README 改成说实话：只有 **shell** 命令里出现这个文件名会
  被拒；并且在同一处点出真正的闸门是谁。

## 决定
选 **B**。**这一条是用户的决定。** 文件头现在把话说明白，并且当场点名真正的闸门：**dsh
自己在写文件时的批准提示**，不是这个 guard。同一处也解释了为什么被拒的**子** agent 从来
不会被告知怎么创建这个文件——创建步骤只发给用户自己的会话（`howToApprove` 与
`ASK_THE_USER`）：既然上面那个洞还在，就不该同时把配方递过去。

这跟仓库里既有的立场是一致的：guard 是安全带，不是锁死的门，文档里必须这么说，不能把它
描述成密不透风的。

## 谁要求的
**选择是干活时撞上的，决定是用户做的。** 这个洞是安全评审在干活时发现的，没有人事先要求
处理；两个选项摆出来之后，是用户选了 B。所以按「有人要求过吗」的判据它仍然是 ADR 而不是
CRD——没有人要求过这件事，它没改变范围也没改变契约，改的是一句话说得准不准。

## 出处
`78639ac`（`git log` 里那条提交信息记的就是这件事），文字在 `host/git-guard.js` 顶部
「Honest limits」那一段，以及两份 README 里对应的段落。
