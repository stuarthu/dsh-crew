# 可测性缺口清单（常备）

这个文件说：**这个产品里有哪些东西，跑不出一个可执行用例来判。**

它是常备的，不是某一次作业的记录。所以按「是什么东西」分组，不按任务号分组——一年后
读到这里的人，看到 `T-05` 三个字什么也想不起来。

它从哪来：QA 的测试计划是一次性的，用例一写出来计划就没用了，作业结束就丢
（`docs/decisions/crd/0006-split-by-lifetime.md`）。但计划里有一段是持久的：**「测不到
什么、为什么」**。那一段搬到这里。所以规矩是——**丢掉一份计划之前，先把它那一段并进这个
文件**；如果这里已经有同一个缺口了，就不用再加一条，只在需要时把话补准。

怎么读每一条：**缺口**（测不到什么）、**为什么**、**该怎么办**、**状态**。

---

## 1. 「文档写得对不对」这类验收检查，没有任何用例能判

**缺口**：验收检查 8、9、10、21、47、53 全是关于文档措辞的——`README.md` 和
`README-zh.md` 说的是不是同一件事、一段话读起来清不清楚、一句解释是不是真的解释了。
QA 没有为它们写用例。

**为什么**：用例能断言「这个字符串在」，不能断言「这句话是对的、清楚的、够用的」。
把一个措辞检查写成用例，只会得到一个钉住某几个词的假绿灯。

**该怎么办**：这类检查要一个读者，不是一个用例——`crew-doc-reviewer`，或者用户自己读。
本次作业（`pm-merge-step`）里这六条**是 PM 一个人核的**，因为用户跳过了文档评审。
也就是说：这六条只有一个人看过，而这个人正是写它们的人。以后再碰到同一类检查，
默认要一个独立的读者。

**状态**：未关闭，而且不会被用例关闭。这是分工问题，不是技术问题。

**2026-08-22 两个可跑的实例（PM 写）。**
- `docs/qa/T-64/case-01` 新加的第 4 道检查要求 `roles/pm.md` 第 2 步**就地**写出「这一步为什么值得」。
  它判得了**结构**（同一句话里同时称出「问一句的成本」和「开局文档错了的成本」），
  判不了**内容对不对**——一句结构齐全而实际空洞的话照样绿。
  **「就地写出的理由说得好不好」永远归人**（文档评审），不归用例。报的人：`crew-qa-C64`。
- `principles.md` 原则 22 的六类问题和 `CRD 0019` 那张表「逐条对得上」这半句，
  `docs/qa/T-68/case-02` 只能钉六个名字在场；**意思有没有走样是 `crew-qa-C43` 人工读出来的**
  （结论：对得上）。报的人：`crew-qa-C43`。
## 2. `roles/*.md` 里的散文规则：用例只能钉字符串，判不了句子

**缺口**：角色提示词是散文。用例能证明 `git merge --no-ff`、`--ff-only`、
`git branch -d crew/`、`publishCheck` 这些关键串还在（`docs/qa/T-01/`、
`docs/qa/T-06/`），也能证明 `roles/pm.md` 里不出现 `{{`；但「这六条设计决定一条不漏地
写清了」（检查 3）、「写清了为什么」（检查 44）这种话，用例判不了。

**为什么**：意思是人读出来的，字符串不是。

**该怎么办**：两件事一起做。改措辞时跑一遍 `bash docs/qa/run-all.sh`——被钉住的串没了
就会红；然后让一个人读那段话。**红了不等于用例错了**：先读失败信息看它点名哪个串，
只有当文档真的按规矩改了（CRD 或 ADR 在），才改用例。

**状态**：未关闭，按设计如此。钉字符串是故意选的下限：它挡住「悄悄删掉一条规则」，
不声称能判文笔。

## 3. 验收检查逐字点名一个字符串时，QA 和工程师的输入必然重合

**缺口**：规矩是 QA 不抄工程师的测试。但有些验收检查本身就逐字写出了要送的命令
（例如检查 32 点名了 `push-ok` 的六种写法），照检查写用例，输入就和工程师的一样。

**为什么**：检查把输入定死了。剩下能不一样的只有壳子和边界——QA 自己搭挂载壳子、
自己加改名、软链接、`bash -c`、全路径删除这些工程师没送的输入。

**该怎么办**：别为了「不一样」去换掉检查点名的输入。把重合写下来，另外加自己挑的边界。

**状态**：未关闭，按设计如此。

## 5. dsh 本身不在这个仓库里跑，所以运行时行为只能在「挂载」这一层验证

**缺口**：用例用假的 ctx 挂载 `host/crew.js`、`host/git-guard.js`，然后断言拼给 PM 的

**该怎么办**：把这类结论按它真实的强度说——「提示词里没有」不是「运行时没有」。

**2026-08-22 补（`crew-qa-C18` 报的行，PM 写）**：同一类的一个具体例子——

## 6. 有些检查只能从源码结构判断（静态检查）

**缺口**：两类话跑不出行为来：

- 「正则只在挂载时建一次，不在每条命令的路径上建」（检查 29）——只能读源码，看
  `new RegExp` 在 `apply()` 里、不在处理每条命令的函数里。
- 「`try` / `finally` 在」（检查 33 的一半）。

**为什么**：这是「代码长什么样」，不是「代码做了什么」。同样的行为可以用别的写法达到，
静态检查会误红；写法对了也不保证行为对。

**该怎么办**：静态检查要**说出来它是静态的**，别当成行为证据。能补行为的就补：
检查 33 的另一半已经补上了——`docs/qa/T-05/case-07-temp-dir-cleanup.mjs` 故意让
`tools/verify-guard.mjs` 中途抛异常，然后看它建的临时目录还在不在。

**状态**：检查 33 的清理行为**已关闭**（由 `case-07-temp-dir-cleanup.mjs` 关闭）。
检查 29 的「只建一次」**仍是静态的**。

## 7. `case-26` 依赖 git 提交历史：浅克隆里它会红，而且答不了检查 11

**缺口**：`docs/qa/T-01/case-26-repo-diff-scope.mjs` 按提交标题里的任务标记搜**整个**
历史，核对「每个任务的提交只动这个任务拥有的文件」（检查 11）。在
`git clone --depth 1` 出来的浅克隆里，那些提交根本没被 fetch 下来，用例**红**，并逐条
打印 `not run`。

**它为什么读提交历史、不读工作树**：工作树只说「现在有哪些改动」，说不出「哪一行属于
哪个任务」——尤其是几个会话同时在改同一批文件的时候。检查 11 的原话是「按任务核对」，
只有提交才带着任务标记。

**为什么**：这是故意选的。另一个做法是「历史不在就当通过」，那会在一个空集合上打绿灯——
一个什么都没检查的绿灯比红灯更坏。所以它把「这里答不了」和「证据真的没了」分开说，
答不了的时候一个 `ok` 都不打。

**该怎么办**：读失败信息，它会告诉你是哪一种。要在这里跑，就
`git fetch --unshallow`（或者别用 `--depth` 克隆）。CI 用 `fetch-depth: 0`，所以 CI 上
历史是全的。**浅克隆里检查 11 无法验证**，不要把那次红当成缺陷。

**状态**：未关闭，按设计如此（宁可红得清楚）。

## 8. 部分克隆（`--filter=blob:none`）不会被认成「历史不可用」

**缺口**：`case-26` 只认两种「答不了」：不是 git 工作树、以及
`git rev-parse --is-shallow-repository` 说 true。**部分克隆**（`git clone
--filter=blob:none`）两条都不满足——提交在，blob 按需现取——所以它会照常往下跑，
一旦取不到对象，失败信息会长得像别的毛病。

**为什么**：这是一个 QA 任务报出来的发现，当时判为 optional（非阻塞），没有做。
真要认，得去看 promisor remote 的配置，比现在这两行判断复杂得多。

**该怎么办**：如果 `case-26` 在一个部分克隆里失败，先想到这一条，别去改用例检查什么。
要修的话，修的是「答不了」的判断，不是被检查的行为。

**状态**：未关闭（optional）。

## 10. 收尾那道门没有封闭的判定词表：`code: maybe` 照样绿

**缺口**：`tools/verify-tasks.mjs` 检查 Verdicts 行的**形状**——一节一行、四个值都在、
每个 `not run` / `skipped` 各带理由、`changes needed` 点名任务号。它**不检查那个值是不是
一个合法的判定词**。所以下面这些全都是绿的：

```
- **Verdicts**：code: maybe ｜ security: 待办 ｜ qa: 大概吧 ｜ doc: ¯\_(ツ)_/¯
```

`docs/qa/T-42/case-20-gate-all-four-values.mjs` 里那条「四个 `pass` 是绿的」正好也证明了
这一点的另一半：门只看到「有一个值」。

**为什么没有用例**：写一条「`code: maybe` 必须红」的用例，等于要求先有一张封闭词表，
而**没有任何 DoD 条目要求过它**。T-40 的工程师自己把这件事报了出来，并且没有替规则做
决定：门是按 `CRD 0011` 写的。

**要说准一点：词表本身并不缺。** `roles/pm.md` 第 11 步已经把允许的写法逐条列了出来——
`code: pass`（或 `code: pass (round 2)`）、`security: pass` 或 `security: skipped — <理由>`、
`qa: pass`、`doc: pass`，没跑的写 `not run — <理由>`，`changes needed` 要点名 `T-<编号>`。
`pass with notes` 不在这张表里。
**2026-08-22 更正**：上面这份抄件原本还写着 `doc: skipped — the user asked for it`，
而 **T-66 把那个值删掉了**——它建立在一个 `roles/pm.md` 从没给过的许可上（全份文件里没有
一句说用户可以关掉文档评审），所以现在 `doc` **没有 `skipped` 值**：没人读过的文档写
`doc: not run — <理由>`，是**评审缺了**，不是**被豁免了**。这一处更正由 T-66 的 engineer
报回，PM 写（按新的「哪类文档谁写」表，这个文件是 PM 的）。**它不改变本条的状态**——
这份抄件是不是最新，和「门读不读这张表」是两件事。
所以缺的**不是那张表，是「把那张表变成门的一条规则」这个决定**：那张表今天是写给 PM 的
规矩，门一个字都不读。
真要变成门规则，还得先说清「值」和「理由」各自的边界——理由是自由文本（本仓库的 Verdicts
行就写着 `not run — 任务还在跑`），值不是。凭空放宽或收紧都会误红，所以这里留一个洞，
不留一条替用户拍板的用例。

**该怎么办**：要关它，先要一个决定——哪些词算合法判定词，写进 `CRD` 或 `principles.md`；
然后加一条门规则，再加一条 QA 用例。**在那之前，这一行只保证「写下来了」，不保证「写对
了」。** 检查脚本自己每次都把这句话打出来：「Passing is not the same as clean … it cannot
prove a review happened — a `code: pass` typed by the PM passes it」。

**2026-08-22 补**（`crew-qa-4` 报的行，PM 写）：第 10 步里「Verdicts 行仍然四个值、
没跑的写 `not run` 带理由、永不写 `pass`」这半截，改到这一天为止**一处机器检查都没有**——
它只活在 `tools/verify-mount.mjs` 那条失败信息的散文里，而没有任何一条 `includes()` 读它。
也就是说从第 10 步删掉 `doc:`、或者删掉「永不写 `pass`」，**全项目一处都不会红**。
现在由 `docs/qa/T-56/case-08-existing-pins-intact.mjs` 直接钉住：四个值各一条断言，
掉哪一个说哪一个（实测只删 `doc:` 时只有那一条红）。
**这不关闭本条**：钉住的是「提示词里写着这句话」，门读的还是形状，`code: maybe` 照样绿。
**这个洞比少一条断言更贵，所以写下来**：`tools/verify-tasks.mjs` 那道门**照旧**要求
`docs/design/tasks.md` 里四个值全在，所以提示词丢了这半截之后，PM 会撞上一道红门、
而它的提示词里没有任何一句话教它怎么写——**门还在，说明书没了**。

**状态**：未关闭，等一个决定（不是等代码）。

## 11. 发布钉子只认 `npm publish`，认不出另外七种发布方式

**缺口**：`tools/verify-mount.mjs` 扫 `.github/workflows/` 下每个文件，把带**活的**
`npm publish` 命令的那些当成发布工作流，然后钉它们：push 触发必须只认 `v*` tag、不能有
`branches:` 过滤、必须在同一个 job 里先无条件跑 `npm test`。

`host/git-guard.js` 认的发布方式比它多。它那条正则（`host/git-guard.js:238`）是：

```js
/\b(npm|pnpm|yarn|bun)\s+publish\b|semantic-release|release-please|gh\s+release\s+create|JS-DevTools\/npm-publish/i
```

除了 `npm publish` 本身，它还认**七**种：`pnpm publish`、`yarn publish`、`bun publish`、
`semantic-release`、`release-please`、`gh release create`、以及
`JS-DevTools/npm-publish`（一个 GitHub Action，不是 shell 命令，所以钉子那条找
「活的 `npm publish` 命令」的正则连形状都对不上）。**七这个数是按「用户会写下的写法」数的**：
`(npm|pnpm|yarn|bun)` 这一段是四种写法，减掉 `npm publish` 剩三种，加上后面四个选择项。
按正则的顶层选择项数只有五个——数法不同，数字就不同，所以这里把数法写出来。

**任何用这七种之一发布的工作流，在 guard 眼里是发布者，在钉子眼里什么都不是**——它不会被
钉，`ok` 行也不会提它。其中 `JS-DevTools/npm-publish` 最值得记住：它是这个仓库最可能用上
的那一种「文件里不出现 `npm publish` 这几个字」的发布方式。

**为什么没有用例**：不是写不出用例，是**不知道该断言什么**。T-44 拒绝了直接放宽：
`gh release create` 常常出现在一个 `workflow_dispatch:` 的手动工作流里，那种文件是对的，
一放宽就会把它误判成红——而「一道会把正确文件判红的门，会教人不再读它」是这个仓库自己写下
的理由（`tools/verify-mount.mjs` 里 T-44 那段注释）。所以要先有一个决定：这七种里哪些算
「必须先跑 `npm test`」的发布，哪些不算。

**该怎么办**：先决定（`CRD`），再改钉子，再补用例。今天这个仓库只用 `npm publish`，所以
**它自己是被盖住的**；这一条讲的是「换一种发布方式之后会静默失去保护」。

**状态**：未关闭，等一个决定。

## 12. `workflow_dispatch:` 配 tag-only 的 `push:`：人可以从任何分支手动发布

**缺口**：一个发布工作流写成这样，钉子和 guard 都不响：

```yaml
on:
  push:
    tags: ["v*"]
  workflow_dispatch:
```

- **钉子**只读 `push:` 那一块，看到 `tags: ["v*"]`、没有 `branches:`，判「tag-only」；
- **guard** 的 `branchPushTriggers()` 读的是同一块，得到同一个答案，于是放一个 crew 子
  agent 的普通分支推送过去；
- 但 `workflow_dispatch:` 让**任何有权限的人**在 GitHub 界面上选任意分支，手工跑这个
  工作流——于是从一个没有打 tag 的分支发布了一个版本。

**为什么没有用例**：和第 11 条同一个原因。`workflow_dispatch:` 本身是完全正常的东西
（重跑一次失败的发布、发一个 canary），把它一律判红会误伤正确的文件；把它判成「必须带

## 14. `scripts.test` 的两个钉子只看紧跟在段落后面的那一个符号

**缺口**：`tools/verify-mount.mjs` 钉住 `package.json` 的 `scripts.test` 里两段命令
（`bash docs/qa/run-all.sh` 和 `node tools/verify-tasks.mjs`）：段落必须在，而且它的退出码
不许被扔掉。判「扔掉」的办法是看**紧跟在那一段后面**的符号是不是 `||`、单个 `|`、单个 `&`、
或者 `;` 后面还有别的命令。所以中间夹了任何东西，它就看不见了：

```
bash docs/qa/run-all.sh --quiet | tee log      <- 钉子读作绿
bash docs/qa/run-all.sh | tee log              <- 钉子读作红（符号紧跟着段落）
```

第一种写法里 QA 的用例照样跑，但退出码被 `tee` 吃掉，用例再也不能把 `npm test` 判红——
和这个钉子要防的那件事一模一样。

**为什么没有用例**：这不是「测不到」，是钉子本身盖不到；而**盖住它要读到那一段后面的下一个
`&&` 为止**——也就是要把整段命令切出来判，比 T-46 那个任务（修两个具体缺陷）宽得多。
T-46 把这个限制在源码注释里点了名，没有顺手放大自己的范围：一个顺手改宽的判断很容易在某个
正当的写法上误红，而「一道会把正确文件判红的门，会教人不再读它」是这个仓库自己的理由
（`ADR 0004`，第 11 条和第 13 条讲的是同一件事）。

**该怎么办**：先决定「一段命令到哪里结束」（读到下一个 `&&`），再改钉子，再补一条用例。
在那之前，**这两个钉子的意思是「段落在，而且紧跟着它的那个符号没有扔掉退出码」，不是
「这一段的退出码一定传得出来」**。给 `scripts.test` 里任何一段加参数或加重定向的时候，
自己看一眼退出码还在不在——绿灯不代表看过了。

**状态**：未关闭，等一个决定（不是等代码）。范围比 T-46 宽，所以那个任务没有做。

## 19. 配置里的角色键没有任何校验：拼错就静默失效

**缺口**：`~/.dsh/.agent-presets/crew/agent.cordis.yml` 里的 `roleAllow`、`roleDeny`、
`roleModels` 都是「角色键 → 值」的对象，而**那个键本身没有任何检查**。写错一个字母，
那一整行就被**静默忽略**——启动日志一个字都不说，用户以为自己的配置生效了，实际生效的是
出厂列表。

`CRD 0016` 这一轮补上的空数组校验**没有改变这一点**，也没有被要求改变它。校验写在
`host/roles-preset.js` 里「按 `ROLES` 逐个角色」的循环里（`for (const role of ROLES)`，
再取 `config?.[field]?.[role.key]`），所以它只看得见**真实存在的**角色键：

- `roleDeny: { engineer: [] }` → 被抓到，挂载期报错（DoD 第 19 条，QA 的 `case-18` 钉着）；
- `roleDeny: { enginer: [] }` → **抓不到**。循环里没有 `enginer` 这个 key，那一项从头到尾
  没被读过，挂载照旧成功。

这一条是 T-51 的 engineer 自己诚实报出来的，QA 复核确认：它**既不是这一轮引入的，也没有
被这一轮变严**。今天的净结果是——**空数组会被拒，拼错的键不会**。

**为什么没有用例**：`CRD 0016` 只定了「空列表必须拒绝启动」，`docs/design/tasks.md` 的
T-51 第 19 条也只写了这一件事。**堵不堵拼错的键是另一条要求，还没有人提。** QA 不为一条
文档没有要求的行为写常驻用例——那等于 QA 自己发明验收标准；也不写一条钉住「拼错必须被静默

**这一段的措辞在 2026-08-21 改准过一次**（`CRD 0016` 的追加一节落地之后）：原来写着

那句话**现在不再成立**。校验已经放宽判据：`undefined` 和 `null`（YAML 里的 `~` 或留空）

值（`"read"`）**一律拒绝启动**（QA 的 `case-21`、`case-24` 钉着九个角色键 × 两个字段 ×
六种形状）。所以**值的形状已经被校验过了，键还没有**——这一条剩下的缺口只有键。

## 45. 判「谁写这份文档」的用例，只判得了带动词的写法

**谁报的**：`crew-qa-C53`，2026-08-22（PM 写）。

**缺口**：`docs/qa/T-71/case-01-engineer-never-writes-an-adr.mjs` 判「谁写 ADR」，
用的是两种窄形状——角色词紧挨一个书写动词（`the PM copies`、`The PM decides`），
或被动的 `written by …`。所以 `the ADR is yours to write` 这种**不带动词贴着角色**的授权，
它一处都看不见。

**为什么窄判据是故意的**：`roles/engineer.md` 里有一句 `Write the ADR yourself and you are both.`，
那是一句**警告**。宽一点的判据（「`you` 和 `ADR` 离得近就算授权」）
会在**说出禁令的那句话上**打红——一条永远红的检查，
而遇到永远红的人最可能做的事是把断言改宽、或者去改文件（第 31 条）。
所以这里选了「**宁可漏，不要永远红**」，代价写在用例的注释里。

**该怎么办**：这一类授权最常见的到达方式是**可写集合里多一条项目符号**，
那一条被同一个用例的「可写侧一处 ADR 都没有」挡住了。没有动词的散文授权只能靠人读。

**状态**：未关闭，按设计如此。这是第 2 条的一个更具体的实例，但它带着一条可复用的取舍——
**判权限的钉子宁可漏，不要永远红**——所以单列。

## 47. `grep '.git'` 保证假绿——DoD 里给的 `grep` 锚串本身可能是正则

**谁报的**：`crew-engineer-T88`，2026-08-22（PM 写，而这一格坏验法是 PM 写的）。

**缺口**：T-88 第 1 格的验法写「那一节里同时出现 `.git`、`node_modules`、`0700` 三个词」。
一个照字面敲的人会写 `grep -c '.git'`——**而 `.` 在正则里是任意字符**，
所以 `git checkout`、`git status` 里的 `git` 都会命中。
**PM 实证**：`printf 'run git checkout and git status\n' > x.txt` 之后，
`grep -c '.git' x.txt` 返回 **1**，`grep -c '\.git' x.txt` 返回 **0**——
**一段完全没提 `.git` 的文字让那一格变绿。**

**为什么它自成一条**：第 28、30、31 条讲的是「锚串不存在」「大小写」「锚串是转述」；
第 21、27 条讲折行和渲染。**这一条讲的是锚串本身被当成正则解释**——
文件名、路径、版本号里的 `.`，正则里的 `[`、`*`、`+`、`?`、`(`，都是这一类。
它的方向是**假绿**，而且是最安静的一种：命令跑了、返回了一个非零的数、看起来在工作。

**该怎么办**：**凡是锚串里有 `.` 或别的正则元字符，验法要么转义（`\.`），
要么用 `grep -F`（按字面）。** 写 DoD 的人给锚串时，问自己「这个串里有没有 `.`」。
这一条**和 `flat` 那一条（第 28 条）是同一族**：命令写下来就已经在判别的东西了。

**状态**：未关闭。**这是 `ADR 0023` 那一族由 PM 在本作业里造的第四次**
（T-86 两格、T-87 一格、T-88 一格），而本作业写下那五种形状、那份 ADR
和这十几条条目之后，PM 每一次写新 DoD 还在犯。**这件事本身要写进验收报告。**
