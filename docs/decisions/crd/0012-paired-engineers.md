# CRD 0012：双 engineer 形状——一个只写测试，一个只写代码

## 谁提的

用户，2026-08-21。开场一句话：「I want to change it, for each task, pm will create 1 engineer
to write test and 1 engineer to write code. The benefits is not only concurrency but also peer
review de facto.」

这份 CRD 记的是接下来那场访谈的结果。访谈用「一轮一个问题」的方式走了十几轮，**用户改了三次
自己的主张，PM 收回过两次说过头的话**，两边都被证据推动过。这些反复留在下面，不删。

## 他们要什么

每一个任务由两个 engineer 做：**A 只写测试，B 只写代码**。两个人各自读 PM 的文档，互不通气。
用户要的不是并发，是**第二双眼睛**——原话：「I want they have different understanding, and that
will cause conflict and push pm to rephrase better.」**分歧就是产品。**

## 为什么——它对着原则 6 的一个真洞

`principles.md` 原则 6 是「测试先于代码，报告必须证明它」。它有一个已知的洞，这个仓库自己已经
承认过一半：**test first 确实产出一份测试，但那份测试是写代码的同一个人写的**，所以测试会被写
成迎合他本来就打算写的代码。原则 6 今天挡不住这件事；挡住它的是另一条规则——bug 的 DoD 一节由
PM 在修之前写（`principles.md` 那一节讲的就是这个）。

用户这次要的是把同一个防线从「只有 bug」推广到「每一个任务」。方向对着一个真实存在的洞。

## 它不是结对编程,这一点在访谈里查清了

PM 一开始拿结对编程（pair programming，XP 最早 12 个实践之一）的数字来算成本，**这个类比是错的**，
查完之后收回：

| | 乒乓结对（ping-pong pairing） | 本 CRD 定的形状 |
| --- | --- | --- |
| 说话 | 全程，双向 | 完全没有 |
| 时间 | 严格交替，一次一小块 | A 先，B 后，各做整块 |
| 检查 | 实时，代码正在被敲出来的时候 | 一次性，写完之后 |
| 谁写测试 | 交替，没人同时占住两半 | 固定，A 一直写 |
| 目标 | **收敛**成一份共同理解 | **不收敛**，分歧是产出 |

结对编程之所以有效，靠的是持续沟通与持续检查；本形状把沟通全部拿掉。所以它不是「去掉聊天的结对
编程」，它是另一门东西：**独立验证**（independent verification）——写检查的人故意不是写代码的人，
来自安全关键工程，不来自 XP。

文档里不许把它叫结对编程。叫它双 engineer 形状。

## 定下来的 17 条

>
> **同一份 CRD 里还有两处也被 0013 推翻了，这里一并点名**（文档评审第 14 条抓到的，
> 因为上面那行指针只提了三个条号，而一个从头读下来的人会在九十行之后撞上它们）：
> 「看过又否掉的六个想法」表里 **worktree 那一行**，以及
> **「独立性是安全带,不是锁——写文档时必须这样说」整节**。
> 后者尤其危险，它是一条**给写文档的人的指令**。两处现在都只适用于**合并之后**：
> 写代码阶段 B 的树里没有测试文件，那是一道锁，不是安全带。


**形状与顺序**

1. 每个任务两个 engineer：**A 只写测试文件，B 只写产品代码**。
2. **A 先。** A 写好测试文件，跑一次，拿到红灯，然后 B 才开工。
   （初稿是「两个同时开工」，被一个竞态否掉：B 在同一个工作目录里同时写代码，A 那一次运行可能
   撞上三种状态——B 还没落代码（干净的红，要的就是这个）、B 的代码已经对了（根本没有红）、
   B 的代码写了一半语法都不通（**假红，长得和真红一样**）。`roles/engineer.md` 里
   「A false red is not evidence」那一节讲的正是这件事，这个方案把它搬进了一个任务内部。）
3. B **从头到尾不读测试文件**。靠自觉，**不加申报规则，不做 worktree 隔离**（见「否掉的想法」）。
4. B 干活期间**不跑新行为的测试**，但**必须**跑 lint、类型检查、项目现有的整套测试、编译。
   「闭眼」指的是新行为没有检查，**不是什么都不跑**。这句话必须写进 persona，否则会被读成
   「写完直接交」，连编译不过的代码都会送到 PM 手里。
5. B 写完之后跑 A 的测试**恰好一次**，报原样结果（绿或红）。**不许反复跑到绿。**
   （反复跑会让整套东西塌回普通 test first，而且是最坏的一种：B 会把每一次不一致都当成
   「我的代码错了」改掉，**分歧一次也不会上报**，PM 永远学不到文档有歧义。而且失败的断言消息
   本身就在泄露测试内容——只跑一次时这个泄露无害，反复跑时它就是驱动 B 的东西。）

**分歧怎么走**

6. 两个 engineer 之间**没有横向通道，不对话**。
   （用户先问「so pair engineers should talk to each other?」，PM 指出这撞上 flat 规则；用户随后
   自己否掉了它：「do we really need to allow 2 engineers talk to each other? if pm/user decide,
   do we still need they talking?」——不需要。理由见「否掉的想法」第一条。）
7. 测试挂了：**两边各自先查自己那一半一次**。
8. 仍然不一致 → **分歧写下来交 PM** → PM 定不了 → **交用户**。
9. **写测试的 agent 不能为了消除冲突而弱化断言。** 只有 PM 能批，而且改动必须能追回 DoD 一节的
   原话。这是把 `roles/engineer.md` 现有的「测试一旦通过，绝不删除，绝不弱化」往外延一格。
   它挡的是一个**安静的**失败：两边都让步，最后在一个谁都没拿文档核对过的答案上会合，测试全绿，
   而 DoD 一节从来没被满足。

**什么时候用**

10. 双人形状与今天的单人 test first **并存**。单人形状**一个字不改**。
11. 哪个任务用哪种，**由用户定**，写在 `docs/design/tasks.md` 的任务行里，用户在第 5 步确认整份
    文档时一起盖章。
12. PM 给的是**一个默认值加一份例外清单**，不是一行一问。一个作业五十个任务不等于五十个决定
    ——crew 存在的一半理由就是保护用户的注意力。
13. PM 的**推荐必须有具体依据**，只能是这几类：这一行的 DoD 措辞自己都写不锋利；这一行坐在一个
    模块边界契约上；做错的后果是钱、权限或数据丢失；这块地方以前的任务出过缺陷。
    成本那句话**写成估计，不写成事实**。

**证据与记录**

14. code reviewer 手里的证据 = **A 的红灯 + B 的一次性结果 + 分歧记录**。
15. **首次会合全绿，只能报「两份理解对上了」，绝不能报「文档是清楚的」。** 理由见下一节。
    这套东西**不是最后一道网**：QA（在后面、闭眼、自己写用例）和 code reviewer 原样保留。
16. `roleModels` **不配**不同模型，两边同模型。理由见下一节。
17. DoD 措辞被一次分歧改进之后，落回 `docs/design/tasks.md` 的任务行（七个去处里
    「一个 DoD 条目自己的措辞」那一条）。**谁批**照抄 CRD 那条判据：
    - 意思没变、只是说清楚了 → **PM 自己改**，里程碑评审时报告；
    - 「done」的含义变了（多一个条件、边界移了、少一项）→ **是范围，当场要用户的 yes，而且它
      自己就该是一个新的 CRD**。

## 它证明什么,不证明什么——这一节推翻了 PM 自己前面说过的话

PM 在访谈中说过「首次会合全绿是最强的结果」。**查完证据之后收回：说过头了。**

| 来源 | 日期 | 说了什么 |
| --- | --- | --- |
| Cockburn & Williams, *The Costs and Benefits of Pair Programming*（Utah 实验） | 1999 / 2001 | 结对多花约 15% 时间，缺陷少约 15%；结对代码通过 90% 验收测试，单人 75%。**注意那 15% 是两个人分担一份工作**，本形状是两个人各做一份。 |
| Knight & Leveson, *An Experimental Evaluation of the Assumption of Independence in Multiversion Programming* | 1986 | 同一份规格、两所大学、27 个独立版本、一百万用例。**独立开发的程序不独立失败**，约 50% 的缺陷是多个版本共有的。 |
| *N-Version Programming with Coding Agents*（arXiv） | 2026-06 | 5 个 harness（含 Claude Code）、23 个模型、48 个实现、一百万用例。同时失败 **429** 次，独立性模型预测 **115** 次（**3.7 倍**，p≈1.8×10⁻¹⁸⁷）。**换模型、换 harness 不能消除完全相关的失败**：907 个跨 agent 配对里 87 对失败模式完全相关（φ=1），同 agent 52 对。失败**集中在规格说明书薄弱处**。 |

最后一行是对本形状核心假设最坏的消息，必须写在这里：

- 本形状假设：文档有歧义 → 两边读法不同 → 冲突 → PM 被逼着改文档。
- 证据说：文档薄弱 → 两边常常犯**同一个误读** → 它们**一致** → 首次会合全绿 → 什么都不上报。

**所以歧义有两种：一种引起分歧，一种引起一致。本形状只抓得住第一种，对第二种完全瞎，而证据说
第二种很常见**——并且它会以「最好的结果」的样子出现。这就是第 15 条和第 16 条的来源：全绿只是
「两份理解对上了」，而真正兜住相关性误读的是 QA，不是换模型。

## 看过又否掉的六个想法

| 想法 | 为什么否掉 |
| --- | --- |
| **两个 engineer 互相对话** | 用户先提，自己又否掉。结对编程靠**收敛**，本设计靠**不收敛**，两者不能同时要。能说话就会谈判，更强势的一方赢，结果又变回一份理解，而 PM 永远不会知道文档有歧义——信号在私下被消化掉。另外，「两边都对、文档确实允许两种读法」这一类只能由 PM 处理，engineer 谁也没权限动任务行。附带收获：砍掉它之后，「必须先记录再对话」那条规则自动变成多余的；**一条规则因为砍掉一个功能而变得不必要，通常说明这一刀砍对了**。 |
| **两个都写测试,第三个写代码**（PM 提的） | 用户选了「测试 vs 代码」。PM 提它的理由留在这里，因为它指出了本形状的一个真实弱点：**测试 vs 测试的信号是纯的**（同一种产出、直接可比，差异只可能来自读法不同），而**测试 vs 代码的红灯混了三种东西**——文档歧义（要的信号）、A 的断言笔误、B 的普通 bug。PM 拿到的只是「红」，三种长得一样。第 7 条（各自先查自己那一半）就是为了剥掉后两种噪音而存在的，它因此成了整个循环里最忙的一步。 |
| **让两个 agent 各写一份「我的理解」摘要来比对** | 更便宜，但测不出东西：**散文可以含糊**，两边能用同样含糊的词绕过同一个歧义然后假一致。测试写不出含糊的断言——写不出一个断言，除非你决定了具体的值、具体的报错、具体的边界。 |
| **两个独立 worktree 做真隔离** | 唯一真的能防住「B 偷看测试文件」的办法，但它是平台层的活：crew 今天完全没有 worktree 的概念（`host/` 里一个字都没有），角色只有工具级的 allow/deny（`host/roles.js`）。用户选了自觉。 |
| **要求 B 在报告里申报「我没读测试文件」** | 仍然查不了，只是把一次模糊的越界变成一次明确的说谎。用户只取了自觉这一条。 |
| **`roleModels` 给两边配不同模型** | 证据说收益很小（跨 agent 边界不消除完全相关的失败），而且有反作用：两边模型强弱不同，弱的那侧会产生大量**假分歧**，噪音直接淹掉信号。 |

## 独立性是安全带,不是锁——写文档时必须这样说

第 3 条靠自觉。**读一个文件不留痕迹**：两个 agent 共享同一个工作目录，A 必须把测试文件写到盘上
才能跑它，那一刻 B 就能 `cat` 到它，而事后没有任何办法查出这件事有没有发生过。

这和 `host/git-guard.js` 是同一个形状——CLAUDE.md 已经写明它「读命令文本，所以是一条安全带，
不是一道锁」。**本形状的独立性必须用同样的口气写**：不许在任何文档里把它说成有保证的。

## 代价

**都是估计,不是实测。这一行本身就是第 13 条要求的口气。**

- 力气：一个任务多花约 **35%–75%**。（这个区间的上半段原本算进了「叫醒复查要起新 agent」的开销；
  按上面那节的更正，dsh 的子 agent 是可续的，那部分开销不存在。数字保守，不改。）（PM 初稿写的是 **+100%**，**错了，收回**：写的部分确实被
  拆开了，但**理解那部分被重复做了两遍**，而在小任务上理解常常是最大的一块。用户当场指出了这一点：
  「I thought it just split same amount of works from 1 engineer to 2 engineers, no?」）
- 墙上时间：可能**更短**，因为两块大头有一部分同时进行。但账要算全：`A 写测试 + max(其余)` 再加
  对账，可能再加一轮修。**文档锋利就赢，文档松就两边都输。**
- 新增两个角色的维护面：两份 persona、两条 `ROLES` 项、每条 deny 列表变宽、`roles/pm.md`
  长出一个分支（那个文件已经一千两百多行）。
- **整套东西的收益，上限是那份 DoD 一节的质量，而那份 DoD 没有第二双眼睛。** 这是本形状最根本的
  局限，写在这里不藏。
