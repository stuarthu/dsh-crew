# CRD 0004：能并行就并行，串行要有真理由

## 谁提的

用户。他先问「why qa take so many time」，PM 查了磁盘上的时间戳，承认慢有两个原因是
PM 造成的：把四个任务的 QA 塞进一个 agent（当时为了省 agent 名额），以及每个用例都要
「弄坏—看红—还原」。PM 说要把这条教训记进 DoD，用户否掉了这个做法：
「do not remember it in dod, this should be a rule that always run agents as parallel
as possible」。

## 想要什么

把「尽量并行」从一次教训变成 PM 的规则：能同时跑的就同时跑，串行必须有真实的依赖。

## 为什么

现在 `roles/pm.md` 第 9 步的写法是**许可式**的——「文件不重叠时，几个工程师**可以**
同时跑」。许可式的写法给了 PM 一个默认值：一个一个来。于是 PM 会为了省一个可数的资源
（agent 个数）去花一个不可数的资源（用户等待的时间）。本次作业就是活证据：四个任务的
QA 串在一个 agent 里，墙上时间大约是分开跑的四倍，用户直接问了为什么这么慢。

`liveAgents` 默认值现在是 20（CRD 0003），所以「怕开太多」这个理由也没了。

## 会动到什么

- `roles/pm.md`：第 9 步（跑任务）和第 10 步（三道关）的措辞，从「可以并行」改成
  「默认并行，串行要有理由」。
- `docs/principles.md`：新增一条原则，带理由。**号要用文件里下一个空号**——第 16 条是
  本次作业的，第 17 条留给另一个会话的作业，写的时候现场看文件。
- 不动 `host/`，不动 `package.json`，不动 README 和 CHANGELOG（这是提示词规则，不是
  用户可见的行为改变；如果写的人认为用户会注意到，报给 PM，由 PM 决定要不要加）。

## 规则的形状（PM 起草，写的人可以改进措辞，但这几点必须在）

1. **默认并行。** 现在能开的任务，一次全开，写在同一条消息里。
2. **两个任务能同时跑的判据不变**：文件清单不重叠。
3. **串行只为真实依赖**：共用同一个文件，或者后一件必须读前一件写下的东西。
4. **一个 agent 要覆盖好几个任务，是「该拆」的信号，不是「该合」的信号。**
5. **不许拿 agent 数量当串行的理由。** 撞到上限就停下来问用户，不要偷偷串起来。
6. 第 10 步的三道关：两个评审是只读的，永远可以并行；QA 只往 `docs/crew/qa/` 写，也
   可以一起跑。代价要写明白：如果评审随后报出 blocking，QA 这一轮就白跑了——所以风险
   高的改动可以先等评审，但那是一次**明说的选择**，不是默认。

## 代价

不用重做任何已完成的工作。本次作业的 QA 已经在跑，按 crew 的规矩不中途改它的指令，
所以这条规则从下一件作业起生效。

## 决定

accepted。用户决定。
