# CRD 0006：按「活多久」分家——决定进仓库，一次性的进作业文件夹

## 谁提的

用户，在本次作业的代码和文档都落地之后的一段对话里。他连着提了四个问题：QA 用例该不该
进项目自己的测试目录、CRD 该不该放在产品仓库里、DoD 该不该是临时的、运行结果该不该丢掉；
然后自己收敛出了形状，并在「按大小分家还是按种类分家」上听完反驳后选了按种类。

## 想要什么

**按「活多久」分家，不按「谁在场」也不按「活多大」分家。**

**进仓库，持久：**

- **ADR** —— 「怎么做」的决定，**不分活的大小**。小活没有架构师，所以由 **PM 写**。
  ADR 不需要架构师存在，它需要**决定**存在。
- **CRD** —— 「做什么 / 范围 / 契约」的决定，**不分活的大小**。
- **QA 的用例** —— 会一直跑的可执行资产。

**进作业文件夹（`~/.dsh/crew/jobs/<job>/`），一次性，验完就丢：**

- **DoD** —— 它列的验收检查，在全部变成真的那一刻就成了历史。
- **QA 的测试计划** —— 用例一写出来，计划的任务就完成了；那张「检查 → 用例」的表，
  用例本身已经用可执行的形式装了同样的信息。
- **运行结果** —— 现在本来就不落盘（输出只走 stdout），把它写成规则。

**收尾时必须有一个搬运动作。** 一次性文档删掉之前，里面持久的东西必须先搬出去：

- 规则 → `docs/principles.md`；
- 「怎么做」的决定 → 一份 ADR；
- 范围 / 契约的决定 → 一个 CRD；
- 这一次改动的理由和当时的测试数字 → 提交信息（快照断言，不是需要维护的文件）；
- QA 计划里「测不到什么、为什么」那一段 → 一份常备的可测性缺口清单。

「不需要了」必须是**挣来的**，不能是假设的。

## 为什么

1. **现在的规则按「谁在场」分家。** 「PRD 类写 ADR，小活写进 `docs/crew/dod.md` 的
   Decisions 小节」——决定的落脚处由「有没有架构师」决定，而不是由「这是什么东西」决定。
   这是设计上的将就。
2. **按活的大小分家会把同一个毛病再犯一次。** 以后有人问「为什么这个检查放在这一层」，
   他得先知道当初那件活是大还是小。而且 CRD 和 ADR 的形状根本不通用：CRD 全是围绕「已经
   说定的东西要改」（谁提的、范围、代价、要不要用户点头），一个「修这个 bug 有两种写法」
   根本没人提出要求，也没改变用户拿到的东西。
3. **反证就是本次作业**：它是**小活**，却写了 5 个 CRD（0001-0005），全是真的范围变更、
   全要用户点头。如果小活的 CRD 位置被设计决定占了，这五个就没地方去，同一个文件夹里
   会躺着两种意思完全不同的文件。
4. **DoD 是「作业进度」穿了一件文档外衣。** `state.json` 本来就在仓库外（`CLAUDE.md` 的
   理由：让用户的 `git status` 保持干净），DoD 属于同一类。
5. **位置对 agent 没影响**：本次作业给每个 agent 的都是绝对路径，DoD 在
   `docs/crew/dod.md` 还是在作业文件夹里，它们读起来一样。

## 会动到什么

- `roles/pm.md`：第 4 步（写哪种文档、写在哪里）、第 10c 步、第 11 步（提交什么）、
  第 16 步之后的收尾，加上新的「搬运」动作。
- `roles/qa.md`：计划写到作业文件夹；用例仍然进仓库；`roles/qa.md:38` 那句「PM 提交你的
  计划和用例」改成只提交用例。
- `roles/engineer.md`、`roles/architect.md`、`roles/doc-reviewer.md`：把「小活写 DoD 的
  Decisions 小节」换成「小活也写 ADR，由 PM 写」。
- `docs/principles.md`：第 13 条（测试落盘）、第 14 条（文档是唯一通道）、第 17 条
  （谁发现选择、谁不独自决定）要跟着改；可能需要新增一条讲「按活多久分家」。
- `CLAUDE.md` 的 State and documents 一节。
- `README.md`、`README-zh.md`、`CHANGELOG.md`。
- 把 `docs/crew/dod.md` 和 `docs/crew/qa/*-plan.md` 从仓库里移走。

## 代价与协调（这一条最要紧）

**上面有五个文件是另一个会话刚刚交付的东西。** `dsh-crew-09` 在 `bfdc799` 里立的正是
「小活写 DoD 的 Decisions 小节」，写在 `roles/engineer.md`、`roles/architect.md`、
`roles/doc-reviewer.md` 里，加上它随后写进 `docs/principles.md` 的 `## 17` 和
`roles/pm.md` 的那段。本 CRD 会**替换掉它刚立的那条规则**——不是它做错了，是用户在它
交付之后想清楚了更好的形状。

它明确说过它读不了本会话的回复，所以**用户是唯一的通道**。

**因此：本 CRD 的执行被挂起**，等 `engineer-proposes-fixes` 那件作业收尾之后再做，一次
把两条规则对齐。现在就动手会造成两个会话在同一批文件上对着改。

「ok, still in adr」），并同意 DoD、计划、运行结果都是一次性的。
