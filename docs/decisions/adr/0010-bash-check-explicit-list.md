# ADR 0010：bash 检查写成显式的三名清单，外加一道「名字必须存在」的自检

- **状态**：已采纳（推荐），2026-08-21
- **决定人**：architect（`paired-engineers` 作业，拆任务时撞上）。用户要的是「新角色的 bash
  被拿掉必须变红」；**这个检查用什么形状写，没有人要求过**，所以它是 ADR。
- **落在哪里**：`tools/verify-mount.mjs`（T-51）。断言在 `docs/qa/T-51/`。

## 今天的样子，以及它为什么不够

`tools/verify-mount.mjs:651-653`：

```js
if (ROLES.find(role => role.key === "engineer").deny?.includes("bash")) {
  fail("the engineer must keep bash: it has to run the tests it writes");
}
```

它只点名一个角色。`CLAUDE.md` 设计规则 4 自己承认了这个洞：把 `crew_qa` 的 `bash` 拿掉，
**一个检查都不会红**。再加两个靠 `bash` 活的角色，洞变三倍大。

还有一件小事值得记下：这一段**没有 `ok()`**。它只会失败，从不报告自己跑过。所以读一次输出，
读者分不清「它通过了」和「它根本没跑到」。

## 看过的三个选项

| 选项 | 好处 | 代价 / 为什么输 |
| --- | --- | --- |
| **A（推荐）显式清单 `["engineer", "test_engineer", "code_engineer"]`**，逐个判，失败信息点名是哪个角色；**外加一道自检**：清单里每个名字都必须能在 `ROLES` 里找到，找不到就红 | 读代码的人一眼看见被守着的是哪三个。失败信息能点名。**自检把这个选项唯一的真毛病堵住了**：改名不会让检查静静地变成空跑 | 加第四个靠 `bash` 活的角色时，**没有任何东西提醒你**要把它加进这份清单。这是真代价，见下面「它不证明什么」 |
| **B 从 `ROLES` 按名字模式推**，例如「key 里含 `engineer` 的都要有 bash」 | 以后加第四个 engineer 角色，自动被覆盖 | **它会安静地覆盖零个角色。** 有人把 `code_engineer` 改名成 `coder`，模式就不再匹配它，检查照样打绿——而这正是这个仓库反复吃过的那种失败（`tools/verify-tasks.mjs:75` 的注释：「A green with nothing found is the worst outcome」，以及那里为什么专门加了一条「一个 task section 都没读到就算红」）。而且「名字里带 engineer」是一条约定，不是事实：`crew_qa` 也要 bash，它的 key 里没有 engineer |
| **C 给 `ROLES` 加一个字段 `needsShell: true`，检查每一个带这个字段的角色** | 新角色自动被覆盖，而且不靠名字，靠声明 | 它把「谁要 shell」从**检查**搬进了**被检查的数据**。写 deny 列表的人同时写这个字段，那么忘了写字段的角色就不被守着——**同一个人同时持有规则和它的例外**。而且这是一个新的角色表字段，会进 `roles-preset.js`、进用户能覆盖的配置说明、进两份 README 的角色表，为一个三行的检查铺一层新概念，不值 |

## 决定

**选 A，而且那道自检不是可选的。** 没有自检的 A 就是 B 的毛病换了个位置。

写下来的形状（措辞由 T-51 定，这里只钉意思）：

1. 一份显式的角色 key 清单，三个名字；
2. 清单里每个名字都要能在 `ROLES` 里找到——找不到就 `fail`，并说清是「清单过期了，
   不是角色坏了」；
3. 三个角色逐个判 `deny` 里有没有 `bash`，失败信息**点名是哪一个**；
4. 三条都过，打一个 `ok()`，把三个名字打出来。**今天那一段没有 `ok()`，顺手补上**——
   一个只会失败、从不报到的检查，读者分不清它通过了还是没跑到。

## 它不证明什么

- **它不保证第四个靠 `bash` 活的角色会被守着。** 加角色的人要自己把名字加进清单。
  `CLAUDE.md`「Adding or changing a role」那份清单要补一步，说明这件事。
- **同一笔账在 `tools/verify-mount.mjs` 里还有两处**（第二轮点名的）：CRD 0006 那份文件名清单
  （今天 `["engineer.md", "architect.md", "doc-reviewer.md"]`）和 CRD 0010 那份（今天六个文件）。
  它们也是显式清单，所以**一份新 persona 不在里面就没人守着它**。T-51 的 DoD 第 16 条把两个
  新名字加进这两份清单；`CLAUDE.md` 要补的那一步同时管这三份清单，不只是 bash 那一份。
- **`crew_qa` 故意不在这三个里面。** 本作业不许改 QA 的任何行为（PRD「不在范围内」），
  把 QA 加进来是一处新的行为约束，不是这次的范围。`CLAUDE.md` 规则 4 记着的那个洞因此
  从「三个里的一个」缩到「QA 一个」，**这一条必须由 QA 写进 `docs/qa/gaps.md`**，
  不许悄悄留着。**它有一个承载点**（第二轮补的）：**T-51 的 DoD 第 17 条**。活由 QA 做
  （`docs/qa/` 是 QA 的家，engineer 不碰它），但没有那一格，这条要求就会像 `CRD 0010` 记的
  那次事故一样——检查离它管的工作太远，然后没了。验法：`grep -n 'crew_qa' docs/qa/gaps.md`。
