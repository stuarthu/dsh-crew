# CRD 0011：用 `npm test` 里的检查守住评审门，不用 git 钩子

## 谁提的

用户，2026-08-21。先提的是 git 钩子（"how about a git hook?"），并说"yes, let
the reviews judge it first"——先让评审判断这个设计。评审判它不成立，用户改采评审给的替代品。

## 他们要什么

一个**没法被忽略**的东西，保证「代码评审 + 文档评审通过」这道门在说"做完了"之前
真的走过。起因是这次作业里 PM（我）跳过了 T-09..T-31 大约 20 个任务的代码评审、
以及第一批之后所有的文档评审，而且**只在用户问起来的时候才说**。

## 为什么

漏掉评审这件事，当时没有任何东西会红。`docs/design/tasks.md` 的 Verdicts 那一行
是这次补上的记录，但它只是一行字：空着也没人拦。

## 被评审否掉的第一个设计：git pre-push 钩子

代码评审给了两条理由，我复核过，都成立：

1. **`pre-push` 看不见 tag 推送带的提交。** 而这个仓库唯一不可撤销的动作，就是
   `v*` tag 触发 `.github/workflows/publish.yml` 发 npm。钩子拦不到唯一真正需要
   拦的那一次推送。
2. **钩子不跟着仓库走。** `git clone` 不带 `.git/hooks/`，`--no-verify` 一句话
   绕过。（评审同时更正了我一个错处：`git push -n` 是 `--dry-run`，不是
   `--no-verify`。）

钩子从未落盘，所以这条 CRD 不撤回任何已有行为。这个否定进 `principles.md` 的
「看过又否掉的想法」表，免得下一个人再搜一遍。

## 采纳的设计

新增检查文件 `tools/verify-tasks.mjs`，挂进 `package.json` 的 `scripts.test`。

它读 `docs/design/tasks.md`，**只认标题形如 `## T-<数字>` 的小节**。`## T-23 / T-24`
这种一个标题带两个任务号的，算一个小节，一条 Verdicts 行就够。其他任何标题一概不看，所以
`## Verdicts 这一行怎么读` 和那几个附录小节**不需要单独的例外规则**。

对每个这样的小节，它要求恰好一条 `- **Verdicts**：` 行，并逐个检查四个值。判红的条件
（用户 2026-08-21 定，见下）：

1. 小节没有 Verdicts 行 → 红；
2. 四个值缺任何一个（`code` / `security` / `qa` / `doc`）→ 红；
3. **某个值是 `not run` 或 `skipped`，但没有紧跟一句自己的理由 → 红。**

「自己的理由」的形状是 `not run — <理由>` 或 `skipped — <理由>`，破折号后面必须有字。
**行尾一个笼统的括号不算**——它机械上说不清自己覆盖了哪几个值，而这次作业的记录正好是
这种：23 行的行尾括号说的是代码评审和文档评审，对同一行里的 `security: not run` 和
`qa: not run` 一个字都没说。

它同时把总数大声打出来：多少个 `not run`、多少个 `skipped`。**通过不等于干净。**

比钩子强的地方：

- 它在 `npm test` 里，所以 **push 时 `test.yml` 跑它，tag 时 `publish.yml`
  发布前也跑它**——正好盖住钩子漏掉的那一次推送。
- 它跟着仓库走，`clone` 就有，`--no-verify` 绕不过它。

## 它证明什么，不证明什么

**必须写进文档，不许含糊。** Verdicts 是 PM 填的，评审员按设计不能写文件
（`principles.md` 12），所以：

- 检查能证明**这一行被写下来了**；
- 检查**不能**证明评审真的发生过。PM 直接写 `code: pass` 也是绿的。

它的价值是把「漏掉」从"月底才发现"变成"当天变红"——这正是这次出问题的地方。
「PM 撒谎」这个洞没有任何自动检查能补，只能靠 Verdicts 留在 git 历史里。
这跟 ADR 0004 记的那笔交易是同一类：钉子挡的是遗忘，不是恶意。

## 代价——量过之后，比初稿写的重

没有要重做的代码，纯新增。但连带成本是真的，PM 初稿把它写轻了。落地前量的实数
（2026-08-21，`docs/design/tasks.md`）：

- **35 个任务小节，只有 33 条 Verdicts 行**——`T-23 / T-24` 和 `T-25 / T-26` 这两个
  合并小节没有这一行，合计 4 个任务号没有；
- 那 33 条里，**33 条全都含 `not run`**。一条干净的都没有：连唯一两条有 `code: pass` 的
  （T-01、T-05），`doc` 也是 `not run`。

（初稿写的是 29 / 27 / 27，是 T-32..T-39 的小节补进去之前的数。文档评审同时更正了另一处：
说「唯一两条 `code: pass（3 轮）`」是错的——只有 T-01 是三轮，T-05 是两轮。）

所以「`not run` 就红」这条规则一上线，`npm test` 会红在 33 个小节（35 个任务号）上，而且一直红，
除非补跑大约 25 个任务的代码评审、安全评审和 QA。这不是意外，是这次作业真实欠下
的账：PM 跳过了评审，而且只在用户问起时才说。

**这条 CRD 因此留了一个待定项**，见下。

## 决定

**accepted**，用户，2026-08-21。理由：它把漏掉评审这件事变成当天可见，而且盖住了
钩子唯一盖不住、也唯一不可撤销的那次推送。

## 这 32 条历史记录怎么算——用户已决定

`not run` 是不是就该红，PM 不自己定——PM 是在给自己那条认罪记录定判罚标准，立场不干净。
交给用户，2026-08-21 答复：**选 B**。

摆给用户的四个选项，和它们各自的代价：

| | 规则 | 代价 |
| --- | --- | --- |
| A | 把历史记录改成更准的措辞（后半段**确实**过了一轮迟到的批量评审，写 `not run` 是低报） | 大部分转绿。**PM 建议不做**：这是 PM 在改自己的认罪记录，方向对自己有利，先例坏 |
| **B** | **门管的是「诚实和可见」：缺行、缺值、或 `not run` 不给理由 → 红。给了理由 → 绿，但总数大声打出来** | **PM 要给 32 行逐值写清为什么。账还在，只是从「沉默」变成「写明」** |
| C | `not run` 就红，补跑 | 最干净。约 25 个任务的代码评审 + 安全评审，加 28 套 QA 用例 |
| D | 划一条时间线，以上算历史，只对新任务生效 | PM 不建议：豁免口子会长大 |

**B 为什么是对的那一个**：它抓住的正是这次真正做错的事——PM 跳过了评审，而且**什么都没说**，
是用户开口问才发现的。它不强迫每条评审都发生（规则本来就允许
`security: skipped — <理由>`），它强迫的是**每一次跳过都留下一句话**。

**B 认真执行的代价，量过**：37 条 Verdicts 行里 32 条含 `not run`。其中只有 2 行完全没有
理由，30 行有行尾括号——但那些括号说的是代码评审和文档评审，对同一行的 `security: not run`
和 `qa: not run` 什么都没说。所以逐值规则下这 32 行都要改，其中约 28 次要写下「PM 没有判断
这些改动是否触发安全评审的条件，直接跳过了」。**那是认账，不是借口。**

## Applied

待定项已答（B），所以 DoD 现在写得出来了。

**这份 CRD 把活交给了五个任务，全部点名，条数都是数过的：**

| 任务 | 做什么 | DoD 条数 |
| --- | --- | --- |
| **T-40** | `tools/verify-tasks.mjs` 加 `package.json` 的 `scripts.test` | **8** |
| **T-42** | QA 的 25 个用例、`run.sh`、`gaps.md` 第 10–12 条 | **10** |
| **T-45** | `roles/pm.md` 第 11 步、`CLAUDE.md`、两份 README、`CHANGELOG.md` | **7** |
| **T-46** | `tools/verify-mount.mjs`：`scripts.test` 那个钉子跟着扩到第二段 | **8** |
| **T-47** | `principles.md`：否掉的钩子进「看过又否掉的想法」表，这道门进原则 20 的表 | **7** |

**这一行原来写的是「T-40 … DoD 一节由 PM 在开工前写，7 条」——两处都错**：T-40 的 DoD 是 **8**
条，而且这份 CRD 明明把活交给了五个任务，Applied 只点了一个。**同一节的教训就是「真正管用的是
CRD 的 Applied 里点了名字」,而它自己只做到五分之一。**这是文档评审第 6 条抓到的。
- **PM 自己的那一份**：32 条 Verdicts 行逐值补理由，**外加给 `## T-23 / T-24` 和
  `## T-25 / T-26` 补上它们根本没有的那两条行**。不补完，门一挂上 `npm test` 就是红的
  ——这是 B 的设计意图，不是意外。

**这一节自己犯过一次同样的错，记在这里不删。** 初稿把 PM 那份写成「32 条逐值补理由」，
**没有提那两个合并小节**——而本 CRD 在四段之前的「代价」一节里刚刚数过它们。T-40 交工时
门是红的，红的正是那两条缺失的行，而它翻回来发现分配工作的时候把它们丢了。

这就是 `CRD 0010` 那条教训的第二次发生：**一个 CRD 点名了 blocking 项，不等于有人会去做它。**
第一次是 `CRD 0010` 自己，这一次是它的下一份。真正管用的不是「CRD 里写了」，是「CRD 的
Applied 里点了名字」——而这一次救回来的也不是流程，是那道门自己变红。

（文档评审点名了这一条：`principles.md` 原则 20 的表里「a change to scope, a DoD item, the
milestone list or a contract」那一行要求 CRD 写清「它加的 DoD 项去了哪个任务、几条」，而初稿一个
任务号都没写。**这里原来写的是「`principles.md` 845」——一个行号。行号会动（那一行现在是 850），
而这个仓库自己的规则就是「指针要点名它指的东西，不是它的编号」。**`CRD 0010` 自己的教训就是"一个 CRD 说自己有 blocking 项，
不等于有人会去看"——没有归属的 CRD 正是被忘掉的那一种。）
