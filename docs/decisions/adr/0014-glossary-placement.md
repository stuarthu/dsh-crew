# ADR 0014：用词表在 `principles.md` 里写成一节独立小节，不编号，标题英文 `Words we use`

- **状态**：已采纳（推荐），2026-08-21。**第二轮补了一件事**：小节标题定成英文
  `Words we use`（v1 只说了「不编号」，没说标题写什么，而钉子需要一个确定的串）。
- **决定人**：architect（`paired-engineers` 作业，拆任务时撞上）。用户要的是「用词必须精确，
  加一张用词表」，PRD v3 已经定了它进 `principles.md`；**它在那个文件里放在哪一层，
  没有人要求过**，所以它是 ADR。
- **落在哪里**：`principles.md`（T-52）。

## 选择是什么

PRD v3 定了两件事：用词表有四条（单元测试、QA 用例、项目的测试命令、契约测试），
它进 `principles.md`。没定的是：**它是原则 22？是原则 21 的一部分？还是一节不编号的小节？**

这不是排版问题。`principles.md` 里**编号意味着一条规则**，每条都带「规则 / 为什么 / 承载它
的文件 / 外部来源」四段。用词表不是规则，是定义。

## 看过的三个选项

| 选项 | 好处 | 代价 / 为什么输 |
| --- | --- | --- |
| **A（推荐）一节不编号的小节**，标题 `Words we use`，放在原则 21 之后、`What we looked at and did not take` 之前 | **它服务好几条原则**（6 讲单元测试先于代码、13 讲测试落盘、21 讲双人形状），还服务 `roles/qa.md`。放在任何一条原则里面都会显得只对那一条有效。而且**这个文件已经有这种形状的小节**——「What we looked at and did not take」和「Keeping this file honest」都不编号——所以不新增概念 | 一个按号找东西的读者会漏过它。用交叉引用补：原则 6 和原则 21 各指一次 |
| **B 写成原则 22** | 有号，好引用，和其他规则并排 | **一个号在这个文件里是一句承诺**：有规则、有理由、有外部来源。用词表没有外部来源——它是本仓库自己的用词，而且是从现有用法里数出来的（`roles/qa.md` 里 case/用例 51 次、「QA test」0 次；「unit test」四处在用）。给它一个号，就得为它编一个「外部来源」，或者留一个空段落，两样都在削弱这个文件里编号的意思 |
| **C 塞进原则 21 里面** | 离新角色最近，读原则 21 的人一定看到 | 它把一张给**整个仓库**用的表，锁在一条只讲双人形状的规则里面。以后单人形状的 engineer 要查「单元测试和 QA 用例的区别」，得先读一条和它无关的规则。**范围写错了** |

## 决定

**选 A：不编号的独立小节，标题 `Words we use`。** 加两处交叉引用：原则 6 和原则 21 各写一句
「用词按 `Words we use` 那一节」。

**标题为什么是英文（第二轮定的）。** `principles.md` **全文 0 个中文字符**，而且它现有的两节
不编号小节都是英文标题（`What we looked at and did not take`、`Keeping this file honest`）。
一个中文标题会是这个文件里唯一的中文，而且它会让钉子变成假的——`grep -n '## 用词' principles.md`
在一份英文文件上**永远不会命中**，那不是一个弱检查，那是一个不存在的检查。
所以：**标题写 `Words we use`，钉子是 `grep -n '^## Words we use' principles.md`。**
同一条道理管住整份任务表：钉子要用**目标文件那门语言**里的名词或路径。
本仓库里可以钉中文串的只有 `README-zh.md`（361 行中文）和 `docs/` 下面这些中文文档。

**顺带定死一条硬规则，写进那一节**：一句话如果可能同时指其中两样，必须用精确名词；
**光写「test / 测试」只允许出现在故意指「上面任意一种」的地方。**

**并且明写一条禁令**：不要写「QA test」。它把「test」这个字又放回来，等于把刚分开的两样重新
粘在一起。仓库里现成的一对是 **unit test（单元测试）** 对 **case（QA 用例）**，两个不同的
名词，本作业沿用，不发明新词。

## 清理的边界，抄在这里因为它最容易被越界

只清理本作业本来就要动的文件：`principles.md`（原则 6、原则 21、用词表本身）、
三份 engineer persona、`roles/pm.md` **新长出来的那个双人分支**、`roles/code-reviewer.md`、
`CLAUDE.md`、两份 README。每一处都由已经拥有那个文件的任务顺手做，**不新开任务**。

**明确不做：把整个仓库每一个 bare「test」都改掉。** `roles/pm.md` 一千两百多行、
`principles.md` 一千多行，全库改字是一次巨大且危险的改动，而且大部分位置今天并不含糊——
只有一个 engineer 的时候「test first」是清楚的。**含糊是新角色带进来的，清理跟着新角色走。**

## 代价

- **仓库里会同时存在被清理过的段落和没被清理的段落。** 一个读者可能在同一个文件里看到
  精确名词和 bare「test」并存。这是有边界的清理必然的样子，写在那一节里说清楚，
  比装作全库统一了要好。
- **不编号的小节更容易被漏读。** 靠两处交叉引用补，补不满。
- **它可以被检查，但只能检查存在性**：用词表在、四条齐全、`roles/qa.md` 里没有「QA test」、
  `roles/test-engineer.md` 说的是单元测试且没声称自己写 QA 用例。**没有任何检查能证明某一句
  散文里的「测试」用词正确**，这一条要进 `docs/qa/gaps.md`。
  **这句话自己有一个承载点**（第二轮补的）：**T-52 的 DoD 第 18 条**。活由 QA 做
  （`docs/qa/` 是 QA 的家，engineer 不碰它），但没有那一格，这条要求就会像 `CRD 0010` 记的
  那次事故一样——检查离它管的工作太远，然后没了。验法：
  `grep -n 'ADR 0014' docs/qa/gaps.md`。
